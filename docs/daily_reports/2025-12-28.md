## 学んだこと・気づき

### 1. フィーチャーフラグパターンの有用性

今回、将来的に削除予定の機能を実装する際、**フィーチャーフラグパターン**を採用しました。

**メリット:**
- 環境変数だけでON/OFF切り替え可能（デプロイ不要）
- コード削除前に本番環境で動作確認できる
- 問題発生時に即座にロールバック可能（`RESTRICT_LOGIN=true` に戻すだけ）

**設計のポイント:**
- コメントに「将来的に削除予定」を明記
- 削除対象のコードを明確にマーキング（🔑 絵文字など）
- ドキュメントに削除手順を記載

### 2. 適切な継承構造の重要性

当初、`Admin::AllowedEmailsController` を `ApplicationController` を継承し、`require_admin!` を重複実装していました。

**問題点:**
- コードの重複
- 管理者チェックロジックが複数箇所に散在
- 保守性の低下

**改善:**
- `Admin::ApplicationController` を継承
- `require_admin!` は親クラスで一元管理
- 新しい管理者コントローラーを追加する際も一貫性が保たれる

**教訓:** コード設計時は、既存の構造を確認し、適切な継承関係を保つことが重要。

### 3. マイグレーションの柔軟性

環境変数からDBへの移行マイグレーションを実装する際、開発環境と本番環境で異なる環境変数ソース（`.env` vs `.kamal/secrets`）を考慮する必要がありました。

**解決策:**
- 同じマイグレーションファイルで両方に対応
- `ENV["ALLOWED_EMAILS"]` はRailsが自動的に適切なソースから読み込む
- マイグレーション内でログ出力（`puts`）を活用して動作確認を容易に

### 4. 大文字小文字を区別しない検索のSQL実装

メールアドレスの検索で大文字小文字を区別しないため、以下のSQLを使用しました：

```ruby
active.exists?([ "LOWER(email) = ?", email.to_s.downcase ])
```

**利点:**
- PostgreSQLの `LOWER()` 関数を使用
- ActiveRecordの `case_sensitive: false` よりも明示的
- パフォーマンスも良好

### 5. Initializerファイルの読み込みタイミング

`config/initializers/authentication.rb` を作成した後、サーバー再起動が必要でした。

**理由:**
- Initializerファイルは起動時にのみ読み込まれる
- 開発環境でも、Initializerファイル追加時は再起動が必須

**教訓:** Initializerファイルを作成・変更した際は、必ずサーバー再起動を行う。

### 7. Turbo Streamsのターゲット指定

連絡済みトグル機能で、最初はTurbo Streamのターゲットを`td`要素に設定していましたが、これが原因で要素が消えてしまいました。

**問題:**
```slim
td#notified_status_#{allowed_email.id}
  = render partial: "notified_button"
```

Turbo Streamで`replace`すると、`td`要素全体が置き換えられ、テーブル構造が壊れる。

**解決策:**
```slim
td
  div#notified_status_#{allowed_email.id}
    = render partial: "notified_button"
```

`td`の中に`div`を追加し、その`div`だけを置き換えることで、テーブル構造を保ったまま更新できる。

**教訓:** Turbo Streamsのターゲットは、置き換えても問題ない単位で設定する。

### 8. フィーチャーフラグの一貫性

ALLOWED_EMAILSのDB化では、フィーチャーフラグ `Authentication.restrict_login?` を導入しましたが、最初は `ApplicationController#logged_in?` だけを更新し、`SessionsController#create` の更新を忘れていました。

**問題:**
- `ApplicationController` では新しい `AllowedEmail.allowed?` を使用
- `SessionsController` では古い `User.email_allowed?` を使用
- 一貫性がなく、将来的な削除が困難になる

**解決策:**
- すべての認証チェックポイントで同じメソッドを使用
- 🔑 絵文字でマーキングし、削除対象を明確化
- コメントで「将来的に削除予定」を明記

**教訓:** フィーチャーフラグを導入する際は、すべての関連箇所を漏れなく更新する。
