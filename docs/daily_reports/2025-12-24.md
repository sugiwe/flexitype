### 1. ユーザー名変更制限機能の実装（PR #81）

**背景:**
- ユーザー名は `/@username` 形式でプロフィールURLに使用される重要な識別子
- 頻繁な変更を許可すると以下のリスクがある:
  - いたずら目的での乱用
  - アカウント乗っ取り後の悪用（既存URLの無効化）
  - 予約語との衝突によるルーティングエラー
- セキュリティとユーザビリティのバランスを取った制限が必要

**実装内容:**

#### データベース設計
- [db/migrate/20251223194636_add_username_changed_at_to_users.rb](db/migrate/20251223194636_add_username_changed_at_to_users.rb): マイグレーション
  - `username_changed_at` カラムを追加（datetime型）
  - ユーザー名の最終変更日時を記録
  - 24時間制限の判定に使用

#### 予約語リストの作成
- [config/initializers/reserved_usernames.rb](config/initializers/reserved_usernames.rb): 予約語モジュール
  - 100+ の予約語を定義
  - カテゴリー別に整理:
    - CRUD・RESTful: `new`, `edit`, `create`, `update`, `destroy`, `show`, `index` など
    - HTTPメソッド: `get`, `post`, `put`, `patch`, `delete` など
    - 認証・アカウント: `login`, `logout`, `signup`, `signin` など
    - Typnix固有のリソース: `lessons`, `keymaps`, `categories`, `history`, `shares`, `my`, `practices` など
    - 管理・設定: `admin`, `settings`, `profiles`, `dashboard` など
    - システム・インフラ: `api`, `webhooks`, `static`, `media` など
  - `ReservedUsernames::LIST` として参照可能

#### Userモデルの拡張
- [app/models/user.rb](app/models/user.rb): バリデーションとヘルパーメソッド
  - **バリデーション:**
    - `username_not_reserved`: 予約語チェック
      - `ReservedUsernames::LIST` に含まれていないか検証
      - 大文字小文字を区別しない（`.downcase`）
    - `username_change_allowed`: 24時間制限チェック
      - 新規作成時はスキップ（`return if new_record?`）
      - `can_change_username?` で変更可能か判定
      - エラーメッセージに次回変更可能日時を含める

  - **ヘルパーメソッド:**
    - `can_change_username?`: 変更可能かどうかを判定
      - 初回（`username_changed_at.nil?`）は常に `true`
      - 2回目以降は24時間経過をチェック
    - `next_username_change_at`: 次回変更可能日時を返す
      - `username_changed_at + 24.hours`
      - 初回は `nil` を返す

#### コントローラーの修正
- [app/controllers/my/accounts_controller.rb](app/controllers/my/accounts_controller.rb): 更新処理
  - **変更検知:**
    - `username_will_change` フラグで実際の変更を検知
    - `account_params[:username].present? && @user.username != account_params[:username]`
  - **タイムスタンプ更新:**
    - ユーザー名が変更された場合のみ `username_changed_at` を更新
    - `@user.update_column(:username_changed_at, Time.current)`
    - `update_column` を使用することで、バリデーションをスキップ（無限ループ回避）

#### UIの改善
- [app/views/my/accounts/edit.html.slim](app/views/my/accounts/edit.html.slim): フォーム表示
  - **条件分岐:**
    - `@user.can_change_username?` で変更可能かどうかを判定
    - 変更可能な場合: 通常のテキストフィールド
    - 変更不可の場合: `disabled: true` のテキストフィールド（グレーアウト）

  - **警告メッセージ:**
    - 変更不可の場合、アンバー色の警告ボックスを表示
    - SVGアイコン付き
    - 「ユーザー名は24時間に1回しか変更できません」
    - 次回変更可能日時を強調表示（`<strong>`）

  - **説明文の拡充:**
    - 使用可能な文字の説明
    - フォーマットルール（記号は連続不可、先頭・末尾不可）
    - 文字数制限（3〜30文字）
    - 予約語の例示（admin、api、my など）
    - 24時間制限の明記

**技術的な判断:**

1. **制限方式の選択:**
   - 生涯変更回数制限（例: 3回まで）ではなく、24時間の冷却期間方式を採用
   - メリット:
     - シンプルな実装（`username_changed_at` 1カラムのみ）
     - ユーザーに柔軟性を提供（長期的には何度でも変更可能）
     - タイポ修正のための初回変更は即座に可能
   - デメリット:
     - 生涯変更回数の上限がない（ただし、24時間制限で十分抑止力がある）

2. **初回変更の扱い:**
   - 初回変更（`username_changed_at.nil?`）は即座に可能
   - タイポ修正などのユーザビリティを重視
   - セキュリティ上のリスクは低い（アカウント作成直後の変更は正当なユースケース）

3. **予約語リストの管理:**
   - Initializerファイルに定義することで、コード変更なしに予約語を追加可能
   - アプリケーション起動時に一度だけロード（パフォーマンス最適化）
   - 既存の別アプリでの実績がある方式を採用

**結果:**
- ✅ ユーザー名変更に24時間の冷却期間を設定
- ✅ 100+ の予約語を定義し、システムルートとの衝突を防止
- ✅ UIで変更可能/不可能を明確に表示
- ✅ セキュリティとユーザビリティのバランスを実現

### 2. 練習履歴の無制限化と期間フィルター機能の実装（PR #82）

**背景:**
- 現在、練習履歴は50件までの保存制限があり、古い履歴が自動削除される
- ユーザーから「全期間の履歴を保存したい」「期間別に絞り込みたい」という要望
- データ量的には無制限にしても問題ない（1ユーザーあたり数百〜数千件程度）
- 期間フィルター（全期間・直近1ヶ月・直近1週間）で快適に閲覧可能に

**実装内容:**

#### データベース設計
- [db/migrate/20251223202059_remove_history_limit_from_users.rb](db/migrate/20251223202059_remove_history_limit_from_users.rb): マイグレーション
  - `users` テーブルから `history_limit` カラムを削除
  - デフォルト値: 50（削除前）
  - データ削除を伴わないため、安全に実行可能

#### モデルの修正
- [app/models/user.rb](app/models/user.rb): バリデーション削除
  - `validates :history_limit, presence: true, numericality: { greater_than: 0 }` を削除
  - `cleanup_old_lesson_records` メソッドを削除（不要になった）

- [app/models/lesson_record.rb](app/models/lesson_record.rb): 自動クリーンアップ削除
  - `after_create :cleanup_old_records` コールバックを削除
  - `cleanup_old_records` メソッドを削除
  - 履歴は無制限に保存されるようになった

#### コントローラーの拡張
- [app/controllers/my/history_controller.rb](app/controllers/my/history_controller.rb): 期間フィルター機能
  - **パラメータ処理:**
    - `@period = params[:period] || "all"`: デフォルトは「全期間」

  - **フィルタリングロジック:**
    - `filter_by_period` メソッドで期間別にフィルタリング
    - `"week"`: 直近1週間（`1.week.ago` 以降）
    - `"month"`: 直近1ヶ月（`1.month.ago` 以降）
    - `"all"`: 全期間（フィルタリングなし）

  - **統計情報の計算:**
    - `@filtered_records`: フィルタリング後のレコード（ページネーション前）
    - `@total_count`: フィルタリング後の総件数
    - `@average_accuracy`: フィルタリング後の平均正答率（小数点1桁）
    - 統計情報が期間に応じて変化するように実装

  - **ページネーション:**
    - `@lesson_records`: フィルタリング後 + ページネーション（20件/ページ）
    - `params: { period: @period }` でページネーション時に期間パラメータを引き継ぎ

#### ビューの実装
- [app/views/my/history/index.html.slim](app/views/my/history/index.html.slim): タブUI
  - **Turbo Frames対応:**
    - `turbo_frame_tag "history_content"` でタブナビゲーション + コンテンツ全体を囲む
    - タブクリック時にフレーム全体が更新される（タブのアクティブ状態も含む）

  - **タブナビゲーション:**
    - 3つのタブ: 「全期間」「直近1ヶ月」「直近1週間」
    - 長い期間 → 短い期間の順（ユーザーフィードバックを反映）
    - `data: { turbo_frame: "history_content" }` でTurbo Framesを有効化
    - サーバー側（`@period`）でアクティブ状態を判定
    - アクティブなタブ: ブルーの下線 + テキスト色
    - 非アクティブなタブ: グレー + ホバー効果

  - **統計情報（ミニ版）:**
    - 総練習回数: `@total_count` 回
    - 平均正答率: `@average_accuracy` %
    - 期間フィルターに連動して更新される

  - **履歴一覧:**
    - PC: テーブル表示（6カラム: 日時、レッスン、単語数、正答率、所要時間、ミス数）
    - モバイル: カード表示（レスポンシブ対応）
    - ページネーション: `params: { period: @period }` で期間パラメータを引き継ぎ

  - **履歴なしメッセージ:**
    - 「この期間の練習履歴がありません」（期間フィルター対応）
    - ユーザーフィードバックを反映（「まだ練習履歴がありません」から変更）

**技術的な実装の詳細:**

1. **Turbo Framesの活用:**
   - タブナビゲーションを `turbo_frame_tag` の中に含めることで、アクティブ状態が正しく更新される
   - 最初はタブナビゲーションがフレームの外にあり、アクティブ状態が更新されない問題が発生
   - デバッグ後、タブナビゲーションをフレーム内に移動して解決

2. **サーバーサイドレンダリング:**
   - Stimulusコントローラーを使わず、Turbo Framesのみで実装
   - サーバー側で `@period` に基づいてアクティブタブのスタイルを設定
   - Day 22のトップページのタブとは異なるアプローチ（Stimulusなし）
   - シンプルで保守性が高い

3. **統計情報の連動:**
   - `@filtered_records` を使って、フィルタリング後のレコードで統計を計算
   - `@lesson_records`（ページネーション後）ではなく、全体のフィルタリング結果を使用
   - これにより、正確な統計情報を表示できる

**デバッグプロセス:**

1. **パスヘルパーのエラー:**
   - `my_history_path` が未定義エラー
   - ルーティングを確認: `my_history_index_path` が正しいパス
   - 修正後、タブ切り替えが動作

2. **タブのアクティブ状態が更新されない:**
   - タブナビゲーションが `turbo_frame_tag` の外にあったため
   - タブクリック時に `history_content` フレーム内だけが更新され、タブ自体は更新されない
   - タブナビゲーションをフレーム内に移動して解決
   - サーバー側で `@period` に基づいてアクティブタブのスタイルが設定される

3. **タブの順番の調整:**
   - 当初: 全期間 → 直近1週間 → 直近1ヶ月
   - ユーザーフィードバック: 長い期間から短い期間の方が直感的
   - 修正後: 全期間 → 直近1ヶ月 → 直近1週間

**結果:**
- ✅ 練習履歴が無制限に保存される
- ✅ 期間フィルター（全期間・直近1ヶ月・直近1週間）でスムーズに絞り込み
- ✅ 統計情報（総練習回数・平均正答率）が期間に連動
- ✅ Turbo Framesによる快適なタブ切り替え
- ✅ ページネーション時に期間パラメータを引き継ぎ

## 学んだこと・気づき

### 1. セキュリティとユーザビリティのバランス

**学んだこと:**
- ユーザー名変更制限では、セキュリティ（悪用防止）とユーザビリティ（柔軟性）のバランスが重要
- 24時間の冷却期間方式は、以下の利点がある:
  - タイポ修正のための初回変更は即座に可能（ユーザビリティ）
  - 頻繁な変更は防止（セキュリティ）
  - シンプルな実装（`username_changed_at` 1カラムのみ）
- 生涯変更回数制限（例: 3回まで）と比較して、柔軟性が高い

**今後の活かし方:**
- セキュリティ機能を実装する際は、ユーザー体験を損なわないように配慮
- UIで制限理由を明確に説明し、次回変更可能日時を表示
- 初回変更は柔軟に、2回目以降は制限を設けるアプローチが有効

### 2. 予約語管理のベストプラクティス

**学んだこと:**
- 予約語リストをInitializerファイルで管理することで、コード変更なしに予約語を追加可能

### 8. データマイグレーションの段階的アプローチ

**学んだこと:**
- データクリーンアップは、安全性を確保するために段階的に実施すべき
- 今回の3段階アプローチ:
  1. **Phase 1: データクリーンアップ** - 古いデータの削除、nilデータの自動マッチング
  2. **Phase 2: スキーマクリーンアップ** - 型変更、カラム削除
  3. **Phase 3: データ整合性の確保** - NOT NULL、外部キー、インデックス
- 各フェーズを独立したマイグレーションにすることで、ロールバックが容易

**PostgreSQLの型キャスト機能:**
- `using: 'lesson_id::bigint'` で文字列型の数値IDを安全にbigint型に変換
- Rails標準の型変換ではエラーになるケースでも、PostgreSQLのキャスト構文で対応可能

**外部キー制約の重要性:**
- データ整合性を保証し、存在しないレッスンへの参照を防止
- インデックスと組み合わせることで、パフォーマンスも向上
- `unless index_exists?` で重複インデックス作成を防止

**今後の活かし方:**
- データマイグレーションは必ず段階的に実施
- Phase 1 → Phase 2 → Phase 3 の順で、安全性を確認しながら進める
- 型変更時はPostgreSQLのキャスト機能を活用
- 外部キー制約とインデックスはセットで考える

### 9. 正規表現によるテキスト処理

**学んだこと:**
- グレード表示の短縮形実装で、正規表現の柔軟性を体験
- 問題: "のカワウソ" と "カワウソ" の両方を削除する必要がある
- 解決: `.gsub(/のカワウソ|カワウソ/, '')` で OR パターンを使用
- 単純な文字列マッチ（`'のカワウソ'`）では対応できないケース

**ベストプラクティス:**
- テキスト処理では、複数パターンのマッチングに正規表現が有効
- `|` (OR) を使うことで、複数の候補を一度に処理
- 先に長いパターン（"のカワウソ"）、後に短いパターン（"カワウソ"）の順で指定すると安全

**今後の活かし方:**
- 複数パターンのテキスト処理には正規表現を積極的に活用
- 単純な文字列マッチで対応できるか、まず確認してから正規表現を使う
- 正規表現の順序（長い → 短い）に注意
