### 1. キーマップリセット機能のバグ修正

**問題点:**
- キーマップ編集画面の「デフォルト設定に戻す」ボタンがエラーになる
- エラー内容: `ActionController::ParameterMissing (param is missing or the value is empty: keymaps)`

**原因:**
- `My::KeymapsController#update` で `reset_to_default` パラメータを処理する前に `keymap_params` を呼び出していた
- `keymap_params` の `params.require(:keymaps)` が、リセット時には存在しないパラメータを要求していた

**修正内容:**
- [app/controllers/my/keymaps_controller.rb:42-48](app/controllers/my/keymaps_controller.rb#L42-L48) の `update` メソッドを修正
- 早期リターンパターンを使用して、`reset_to_default` パラメータがある場合は `reset_keymap` メソッドを先に実行
- `active` パラメータ、基本情報のみ更新の場合も同様に早期リターン
- これにより、不要な `keymap_params` の呼び出しを回避

### 4. レイアウトシフト問題の修正

**問題点:**
- タイピング練習開始時に、キーボード表示領域のレイアウトがシフトする
- 特に「入力してください」から実際の文字が表示されるタイミングでずれが発生

**原因:**
- 初期状態（「入力してください」）と実際の文字では高さが異なる
- CLS（Cumulative Layout Shift）が発生し、ユーザー体験を損なっていた

**修正内容:**
- 最小高さ（`min-h-[...]`）を設定してレイアウトシフトを防止
- 初期状態でも十分な高さを確保
- スムーズなレイアウト遷移を実現

## 学んだこと・気づき

### 1. 本番環境データの事前調査の重要性

**教訓:**
- マイグレーション実装前に本番環境のデータ状態を確認することが重要
- 今回は「全ユーザーが少なくとも1つのキーマップセットを持っている」と仮定していたが、実際には持っていないユーザーが存在
- Rails コンソールや SQL で事前確認することで、マイグレーション失敗を防げる

**対策:**
- NOT NULL 制約を追加する場合は、必ず reversible ブロックで既存データを適切に処理
- `find_or_initialize_by` や `find_or_create_by` を活用して、データがない場合の自動生成を実装
- マイグレーション実行前に dry-run 的な確認を行う

### 2. Rails の早期リターンパターン

**学んだこと:**
- コントローラーのアクションで複数の処理パターンがある場合、早期リターンパターンが有効
- 条件分岐をネストさせるよりも、早期リターンで処理を分離する方が可読性が高い

**良い例（今回の修正）:**
```ruby
def update
  return reset_keymap if params[:reset_to_default]
  return set_active_keymap if params[:active]
  return update_basic_info if basic_info_only?

  update_keymaps
end
```

**悪い例（修正前の潜在的な問題）:**
```ruby
def update
  keymaps_params = keymap_params  # reset時にエラー

  if params[:reset_to_default]
    reset_keymap
  elsif params[:active]
    set_active_keymap
  else
    update_keymaps
  end
end
```

### 3. マイグレーションのロールバック対応

**学んだこと:**
- マイグレーション失敗時は、本番環境で `kamal app exec --roles=web 'bin/rails db:rollback:primary STEP=1'` を使用
- Rails 8.1 では複数データベース対応のため、`db:rollback:primary` のように DB を指定する必要がある
- ロールバック後、修正したマイグレーションで再デプロイすればOK

### 4. Kamal のヘルスチェックタイムアウト

**学んだこと:**
- Kamal のデフォルトヘルスチェックタイムアウトは30秒
- SolidQueue などのバックグラウンドジョブ処理の起動に時間がかかる場合、タイムアウトエラーが発生する可能性
- 今回は1回目のデプロイでタイムアウトしたが、マイグレーション自体は成功していたため、2回目のデプロイで正常に起動

**対策案（将来的に検討）:**
- `config/deploy.yml` で `deploy_timeout` を調整
- ヘルスチェックエンドポイント（`/up`）の応答速度を改善
- バックグラウンドジョブの起動を非同期化
